# AF0: actor, history and conflict design

**Reviewed:** 2026-11-08. **Implementation baseline:** `62ac896` (schema v16).
**Status:** design contracts accepted by the maintainer in two review steps;
implementation and AF2 verification are pending. The
[shared checklist](../AI_NATIVE_PLAN_CHECKLIST.md) owns progress.

## 1. Decisions and boundaries

The maintainer confirmed one local Rust project engine shared by a human and
multiple agent sessions; Rust-owned views, branches, locks and history; protection
of later human edits; Stop targeting <=1 second with no late application; and
reopen preserving provenance/locks while requiring fresh authorization.

Selected approach: **conservative change journal alongside snapshots**. Ordinary
undo retains snapshots; selective review/undo uses stable identities, before/after
records and explicit dependency checks. Full event sourcing would require a much
larger command/replay migration. Branch-only review would defer the required
actor-only undo. Neither alternative was selected.

Accepted trade-off: safe edits can occasionally be refused when dependencies are
too coarse or unknown. No automatic rebasing, hidden conflict resolution or
cascading deletion of another actor's work. Revisit finer dependency coverage
after measuring actual refusals, rather than relaxing checks to complete a demo.

The two accepted review steps covered:

1. Canonical branches; session-local views and gestures; server-issued logical
   session capabilities; stable change identities; conservative review/undo;
   explicit unsupported/conflict errors; stale whole-branch refusal.
2. Durable locks and explicit human reclaim; Stop/commit ordering and generation
   fencing; rollback-safe atomic batches; migration/reopen; failure/race tests.

These decisions do not approve AF1 command tiers/profiles, session-mode defaults,
auto-merge, provider selection, Agent/Review placement or the execution queue.
Those remain in [the decision register](../AGENT_FIRST_PLAN.md#5-decisions-pending-from-the-maintainer).

## 3. One project owner, explicit identities

Proposed names here describe contracts, not finalized API/schema spellings.

| Identity/state | Lifetime and ownership |
|---|---|
| Project ID | Durable, generated by Rust; distinguish a project from its current filename. |
| Open-project epoch | New on open/new/close; invalidates all work captured against an earlier document instance. |
| Actor ID | Durable attribution principal. A display name is not proof of identity. The GUI's human identity is bound by the trusted host. |
| Session ID + capability | Ephemeral, server-issued and bound to an actor, project epoch, mode and grants. One per independently controlled agent session. |
| Session generation | Monotonic fencing value, advanced on Stop/resume/revocation. Old work never becomes valid again. |
| Branch ID + head revision | Durable identity and monotonic revision, independent of branch display name. Undo creates a new revision. |
| Entity ID | Stable identity for clips and all selectively editable entities/relations. Fork preserves IDs; duplication creates new IDs. |
| Change ID / transaction ID | Immutable attribution/dependency record; a transaction can group several changes. |
| Lock ID + lock revision | Durable protected scope and owner; lock changes invalidate captured approvals/preparations. |

Rust owns a canonical branch store. Each branch has a project snapshot, head
revision, fork ancestry/baseline and journal references. A session selects a
branch without parking or replacing another session's project. Immutable clones
used for analysis are temporary inputs, not a second authoritative engine.

Session-local state includes playhead, stable-ID selection, targeting, active
sequence/branch, trim focus, command clipboard, gesture transaction and view
preferences. The GUI reads its human view; ghost cursors are explicit observations
of other sessions. An agent cannot move the human cursor by omitting a session.
Invalidated selections are cleared/reported, never retargeted by shifted indices.
Cursor changes do not create project undo entries or dirty the saved document.

Jobs/export records remain project-service owned, each attributed to its initiating
actor, session/generation, branch and captured revision. Session-local queue views
filter those records; actors do not own duplicate export engines. Human authority
can stop any session; agents manage only their authorized jobs. Background results
report their snapshot identity, even when the human is viewing another branch.

### Transport binding

One logical MCP process retains its server-issued capability and supplies it on
each fresh bridge socket. The host validates it before dispatch. Neither a caller
supplied `actor_id` nor a branch name can impersonate the human. Parallel agent
clients receive different sessions even if they use the same model/display name.
Capabilities never appear in project files, logs or media-visible tool results.

Headless MCP and desktop bridge use the same authenticated command context and
policy checks, including dedicated preparation wrappers. GUI commands get a
host-bound context; generic dispatch is not a bypass. Missing/expired identity
must fail explicitly once sessions are required; no fallback to human identity.
Trusted reconnect authorization may bind a new session to a durable actor, but
matching an old actor label from a project file cannot restore grants.

Retries carry a request ID bound to session/generation and a canonical request
hash. A completed retry returns its prior result; a reused ID with different
arguments fails. Lost replies are queried by request ID before resubmission.
Reopen invalidates this session cache; durable change records remain inspectable.

## 4. Journal, coverage and ordinary undo

Each committed change records actor, session attribution (no secret), timestamp,
branch, base/result revisions, command/wrapper ID, transaction ID, affected entity
IDs, before/after values, read dependencies, write footprint and required resource
references. AF4 adds rationale/confidence/review status without changing the
conflict model. Human corrections retain links to the original agent change.

Dependencies include structure, ordering, existence, source media, timing,
automation and effects, not merely the fields returned in a visible diff. For
example, an edit to a clip inserted by an agent depends on that insertion even
if the new edit changes only volume. Ripple operations include every moved clip
and affected relation. Shared media edits include all dependent uses.

Stable IDs are never recycled. Split records source-to-result lineage; new pieces
get distinct identities. Deleted IDs retain tombstones while history references
them. Journal records are immutable; undo, redo, review and correction append new
records referring to the originals. A restored value does not reset revisions.

Command coverage is explicit: precise footprint, conservative whole-branch
footprint, or unknown/unsupported. Before/after comparison can verify writes but
cannot discover all reads. An unexplained write is an invariant failure, not
permission to omit it. Unknown dependency coverage blocks selective review and
actor undo. AF1's availability inventory must expose these limitations.

Ordinary branch-tip undo can use a stored branch snapshot when context, locks
and dependencies permit. It never restores another branch, sessions, grants,
durable locks or the whole journal from an old `ProjectDocument`. Actor-only undo
always follows section 5, even if an old snapshot happens to exist. Redo validates
again; intervening commits cannot be overwritten. Snapshot retention can keep the
existing 100-entry cap, but journal/provenance retention is independent. Pruned
inverse payloads return `history_unavailable`; they do not erase attribution.

Gestures belong to one session/branch and cannot span another actor's history.
Incremental gesture updates use their own bounded publications. Interleaving
changes close or conflict the group; a long drag must not hold the commit gate.
Stop keeps already published updates and discards only uncommitted work.

## 5. Conservative review and conflict rule

For a selected change/transaction, the engine resolves a complete dependency
closure, identifies the source and target branch revisions, validates current
values, permissions and locks, and either publishes one supported transaction or
returns a structured refusal. Review previews carry revisions; clicking Accept
or Reject revalidates them. UI preview is never an authorization token.

### Selective undo or reject of an applied edit

An inverse is allowed only when all of the following hold:

1. The change is applied, inverse data exists, and its footprint is known.
2. Current written values/identities match the expected after-state.
3. No surviving later change, by **any** actor, reads or depends on the effects
   being removed; no incompatible later write or structural dependency exists.
4. Applying the inverse preserves project validation and respects all locks and
   grants. A missing entity or ambiguous relation is a conflict.

Reject does not silently roll back dependent edits. The result identifies blocking
change/entity IDs and reasons. A larger explicitly selected reversible group can
be checked as one unit, but never expands automatically to include human work.
An atomic-batch change cannot be partially undone: request its whole transaction
or receive an explicit indivisible-transaction error.

### Accept an individual proposed change

Require a common, unambiguous baseline and complete read/write coverage. The target
must satisfy the proposal's read dependencies and expected before-state; source
changes required by it must already be accepted with their identity mapping or
explicitly included. Publication records target attribution plus source provenance
and prevents double application. A proposal changed since review must be inspected
again. Unsupported commands, ambiguous legacy IDs and unavailable history refuse.

Rejecting an unapplied proposal records a review decision; it does not mutate the
human branch. Removing applied effects on the agent branch uses the inverse rule.
Whole-branch rejection/discard is separately authorized, checks branch users/jobs
and locks, and preserves required audit/provenance and retained media references.

### Accept a whole branch

The target branch ID and monotonic head revision must equal the recorded target
baseline at fork/rebase establishment. A target edited and then undone is still
changed: identical content alone is insufficient. Check source revision, full
diff, locks, resources, grants and validation before one replacement publication.
A stale target returns a conflict with no mutation; there is no force-overwrite
option in this design. A new explicit baseline/review is needed.

### Examples

| History | Result |
|---|---|
| Agent trims A; human changes unrelated B; undo agent trim | Allowed only with proven disjoint dependencies; preserve B exactly. |
| Agent inserts A; human grades A; undo insertion | Refused: later grade depends on A existing. |
| Agent changes source media used by B; human edits B | Check media dependency; clip IDs alone cannot establish independence. |
| Agent branch fork; human changes target; accept whole branch | Refused, even if target was later undone to matching content. |
| Source proposal depends on another unaccepted source edit | Refused unless the explicit group includes that dependency. |
| Unknown command footprint | Unsupported selective operation; never a guessed merge. |

## 6. Durable locks and human takeover

Locks live in a project-wide registry outside undoable branch snapshots. Each has
an owner actor, protected scope, creation provenance and revision. Clip locks
protect the logical entity across forks; region locks conservatively protect the
specified sequence/track identities and half-open tick interval across branches.
This deliberately prevents a branch switch/merge from bypassing a human lock.

Region protection checks both old and new footprints plus dependencies. Moving
content into/out of a locked range, ripple shifts through it, track deletion and
changes to media/settings affecting it require the lock's authority. Normalization
of region boundaries is explicit; a moved clip's entity lock follows its identity.
Unknown footprint means refusal. Existing track/group `locked` flags remain
editing constraints as well; they are not authenticated actor locks.

Disconnect, Stop and reopen never silently release locks. Without a valid owning
session, an owner can be shown as disconnected; matching a name cannot reclaim it.
The human can explicitly reclaim/release/transfer a lock with an attributed audit
record. Reclaim changes the lock revision and invalidates pending prepared edits.
It grants no permission to apply work captured before reclaim. Human takeover
does not require waiting for the former agent to reconnect.

## 7. Stop, preparation and commit ordering

Each task captures project epoch, actor/session, generation, branch/revision,
request ID, grants/origin approvals, lock revision and cancellation token.
Preparation occurs off the project lock against an immutable snapshot. Long decode,
analysis, inference and render work never runs under the publication gate.

Publication and Stop have a single linearization order under a short shared gate:

1. Build/validate the candidate snapshot, journal and owned staged artifacts off
   gate. Queueing does not authorize publication.
2. Acquire the gate; recheck epoch/generation, stopped state, current branch head,
   policy and lock revisions. Publish snapshot and journal together, or refuse.
3. Stop acquires that same gate, marks the session stopped and advances its fence.
   Then cancel its queued/running jobs, settle replies and schedule cleanup.

An atomic cancellation flag followed by an unguarded write is insufficient: Stop
could fall between the check and write. No filesystem/network I/O or worker join
belongs inside this gate. Large validation/cloning stays outside; implementation
must bound final checks/publication and avoid lock-order inversion/starvation.

If commit wins before Stop, the edit remains visible and attributed and the Stop
result reports that boundary. If Stop wins, that generation cannot publish, even
after human resume. Resume is a trusted human action issuing a new generation;
it does not reopen old requests or recreate expired approvals. Read/status access
for human supervision remains available while agent work is stopped.

Measure click/request-to-fence latency and worker-cancellation latency separately,
targeting <=1 second for both on supported slow-analysis/render paths. Also record
cleanup completion. A blocked native worker may be fenced while still shutting
down; report that state truthfully and fail the cancellation gate if it exceeds
the budget. Use bounded cooperative checks or a terminable worker where needed;
returning early from an async wrapper does not stop its blocking thread.

Prepared results, callbacks, artifact finalization and job updates all check the
captured context. A success-looking late callback cannot resurrect a cancelled
job or apply media. Uncommitted artifacts have exclusive temporary ownership and
are cleaned on failure/cancellation. Committed artifacts are retained while any
branch, undo record or journal reference needs them. Reopen recovery only removes
known incomplete owned artifacts, never arbitrary files beside a project.

External effects already completed (an export or a sent network request) cannot
be undone by Stop. They are separately attributed, permission-controlled and
reported. This limitation never permits a late project-state commit.

## 8. Atomic batches and failure boundaries

Keep existing sequential `steps`/`stop_on_error` behavior explicit. A caller must
request atomic mode. Preflight the entire batch before step 1; reject unsupported
operation types and enforce a documented step/size budget. Supported atomic
batches initially contain only reversible, project-state edits with known effects.

Execute against a private branch candidate; resolve later steps against earlier
staged results. Check actor, mode, profile/grants, origins and locks at each step.
Accumulate dependencies and inverse records and validate the final document.
Publish once with one transaction/undo boundary after current-context checks.
Failure, panic, Stop or stale base discards the candidate, staged history and
selection updates, with no partial events or document dirtying. IDs reserved in
failed work may be skipped; they are never reused as another committed entity.

Initially unsupported in atomic mode: filesystem writes, save/open/new, network,
exports, plugin loading, prepared-media operations, session/lock changes, branch
lifecycle changes and view-only commands. Some can be supported later with a
separately tested transaction contract. An error names the offending step/effect;
there is no automatic downgrade to sequential behavior.

Ordinary commands also need a safe publication boundary. Catching a panic after
in-place mutations does not itself roll them back. A poisoned/untrusted candidate
must never replace the last valid snapshot. An I/O failure before commit is a
failed operation; after an external effect, return its actual outcome separately.

## 9. Migration, save and reopen

Add a versioned migration from v16; choose the next schema number at implementation
time. Persist project/branch/entity IDs, revision/fork records, retained journal
and provenance, and the lock registry in one coherent saved document. A successful
in-memory edit is not claimed crash-durable until the documented save boundary.
Save uses an atomic replacement of a validated coherent snapshot; a failed save
keeps the prior file and the dirty flag. Do not save capability secrets/grants.

Assign missing legacy IDs once and persist them. Preserve uniquely established
identity across forks; index, equal timestamps or shared `media_id` alone cannot
prove that two legacy clips correspond. Ambiguous parked branches receive their
own identities and an unknown-common-baseline marker. Preserve their content for
inspection; refuse selective operations or stale-baseline merge requiring proof.
Legacy edits have unknown actor/coverage, never fabricated human provenance.

Reopen validates duplicate/missing IDs, relation references, revisions and lock
scopes before enabling mutation. Unsupported future versions return a real error.
Sessions, grants, in-flight tasks and ephemeral views start fresh. Provenance,
review decisions and disconnected locks survive. A project-file actor record is
attribution data, not authority. Undo payload pruning never silently removes
durable lock or provenance information.
